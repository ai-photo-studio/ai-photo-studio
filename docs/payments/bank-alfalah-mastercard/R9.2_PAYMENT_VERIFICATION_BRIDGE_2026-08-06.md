# R9.2 Payment Verification Bridge (2026-08-06)

## What changed

`CustomerCheckoutService.getStatus` is now the single, live entry point that
turns a `PaymentAttempt` into `PAID`. Every piece of verification logic it
calls (`handleMpgsBrowserReturn`, `matchRetrievedOrderToAttempt`,
`applyVerifiedPaymentEvidence`) already existed from earlier P4C/P4A packets
and was already fully race-tested — it was simply never reachable from any
route or service. This packet wires it up with no new verification logic and
no new database transaction.

## Verification path

1. Client calls `GET /fixed-orders/:orderNo/payment-status` (existing route,
   unchanged contract).
2. `CustomerCheckoutService.getStatus`:
   - Loads the `FixedOrder` + `PaymentAttempt` and enforces ownership
     (`assertOwnership`, uniform 404 on mismatch/enumeration).
   - **Never reads or trusts any browser return / query-string parameter** —
     the caller doesn't even pass one; `FixedOrderReviewPage` ignores its own
     URL's query string.
   - Only when `attempt.status` is one of `REDIRECT_READY`,
     `CUSTOMER_RETURNED`, `CALLBACK_PENDING`, `AUTHORIZED` does it call the
     gateway at all — a fresh, server-initiated MPGS Retrieve Order request.
   - The retrieved order is matched field-by-field (merchant, order id,
     amount, currency, successful payment state) against the immutable
     stored `FixedOrder`/`PaymentAttempt` by the existing
     `matchRetrievedOrderToAttempt` logic.
   - On an exact match, `applyVerifiedPaymentEvidence` (P4A) commits `PAID` +
     one deduplicated `PaymentEvent` + entitlement + queued execution,
     idempotently, inside its own transaction.
   - On any mismatch, pending, failed, or cancelled result, nothing is
     written; the attempt's existing stored status is returned unchanged.
3. No webhook path is touched. Webhook authentication format remains
   undocumented by the bank, so `handleMpgsWebhookTrigger` stays unrouted, as
   in all prior packets.

## Confirmed production defect found and fixed

`CustomerCheckoutService.createCheckout` previously wrote
`PaymentAttempt.providerRef = checkout.sessionId` when creating the Hosted
Checkout session. `providerRef` is the field P4A's own guard in
`p4a-payment-verified-execution-queue.service.ts` (`runOnce`) treats as the
**verified transaction reference**, set once by a prior successful
verification — a structurally different MPGS identifier from the Hosted
Checkout session id. Writing the session id there meant `providerRef` was
never `null` when real verification evidence arrived, so every first-ever
verification attempt would have failed closed with
`PROVIDER_REFERENCE_MISMATCH` — silently breaking payment confirmation for
every real transaction. Found while building and testing `getStatus` against
a disposable Postgres instance in this same packet (traced with a temporary,
deleted debug script). Fixed by removing the write; `providerRef` is left
unset at checkout creation and is set exactly once by P4A itself. The
network-call gate in `getStatus` was correspondingly changed from
`providerRef` truthiness to an explicit attempt-status allow-list, since
`providerRef` was never a reliable "checkout was initiated" signal.

See `rules.md` for the permanent protection added against this class of
regression.

## Guarantees proven by tests (`customer-checkout.service.pg-race.test.ts`, 11 tests)

- Successful, exactly-matching Retrieve Order response → `PAID`, exactly one
  `PaymentEvent` / entitlement / queued execution.
- Pending gateway result never fabricates `PAID`.
- Forged amount, forged/mismatched order id → rejected, no mutation.
- Wrong-owner actor → uniform 404, zero gateway calls.
- 3 concurrent `getStatus` calls on the same attempt converge to exactly one
  event/entitlement/execution (dedupe via `dedupeHash` unique constraint).
- Extraneous/fabricated actor fields cannot influence the result.
- Zero external calls when no gateway session exists yet (`CREATED`) or the
  attempt is already `PAID`.
- Static scan confirms zero live network calls anywhere in the test file.

## Explicitly out of scope for this packet

- No live Bank Alfalah sandbox/production request.
- No production activation.
- No webhook mutation (auth format still undocumented).
- No change to RunPod, deployment, capture, or production credentials.

## Test coverage note

Playwright's default suite in this repo is mock-only by convention (it never
calls a real backend). The API/response contract of
`GET /fixed-orders/:orderNo/payment-status` is unchanged by this packet —
only the server-side verification internals behind it changed — so the
existing Playwright coverage (including the "refresh payment status performs
GET only" case in `p4e-checkout-ui.spec.ts`, 58/58 passing) remains valid
proof that the UI truthfully displays whatever status the server reports.
The real verification logic itself is proven at the disposable-Postgres
race-test layer above, which is the appropriate and stronger layer for
server-side correctness and concurrency guarantees.
