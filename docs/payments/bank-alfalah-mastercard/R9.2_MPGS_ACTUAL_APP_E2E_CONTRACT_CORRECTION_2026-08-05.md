## 1. Confirmed contract mismatch, repaired

Live-fetched the bank's own v100 REST-JSON API documentation
(`.../api/documentation/apiDocumentation/rest-json/version/100/operation/Hosted%20Checkout%3a%20Initiate%20Checkout.html`)
directly, per this task's instruction that the bank-supplied contract is the sandbox
authority. It specifies:

- **Method: `POST`**, not `PUT`.
- **URL: `POST .../merchant/{merchantId}/session`**, not
  `PUT .../order/{orderId}/checkout`.
- **`interaction.merchant.name` is a REQUIRED field** (string, 1-40 chars).

The existing `p4c-bank-alfalah-mpgs-gateway.service.ts` (merged via PR #118/#137) used
`PUT .../order/{orderId}/checkout` and never sent `interaction.merchant.name`. This is
consistent with -- and very likely fully explains -- the original P4C sandbox smoke
result (`structural HTTP 404` on Hosted Checkout initialization,
`P4C_SANDBOX_SMOKE_EVIDENCE.md`): the endpoint the adapter was calling has never existed
on this gateway. It is also consistent with why the later ad-hoc diagnostic script in
`P4D_PURCHASE_FINAL_TEST_2026-08-05.md` (which independently used `POST .../session`
with `interaction.merchant.name` set) reached a structurally different `HTTP 400`
business-validation response instead of a `404`.

**Repair applied** (smallest change matching the confirmed contract):
- `initiateHostedCheckout` now sends `POST {baseUrl}/api/rest/version/{v}/merchant/{merchantId}/session`.
- Request body gained `interaction.merchant.name`, sourced from a new required
  (when enabled) config field `BANK_ALFALAH_MPGS_MERCHANT_NAME` -- validated the same
  way `BANK_ALFALAH_MPGS_RETURN_URL` already is (fails closed 1-40 chars).
- `retrieveOrder` (`GET .../order/{orderId}`) is unchanged -- the bank's `merchant.name`
  requirement is specific to `INITIATE_CHECKOUT`, confirmed by the same doc page.
- No change to Basic Auth construction (`merchant.<Merchant ID>` username, unchanged),
  API version handling, or the verification orchestrator
  (`matchRetrievedOrderToAttempt`/`verifyMpgsPaymentByRetrieveOrder`).

## 2. Confirmed defect: checkout route was unreachable (found only via the real app)

`customer-checkout.controller.ts`'s routes were mounted at
`/orders/:orderNo/checkout` and `/orders/:orderNo/payment-status` -- byte-for-byte
identical to the pre-existing legacy `OrderController.createOrderCheckout` route
(`order.routes.ts`), mounted *earlier* in `index.ts`
(`createOrderRouter(config)` before `createRestorationRouter(config)`). Express matches
the first-registered handler for an identical method+path, so every real "Pay securely"
click in the actual running app was silently handled by the legacy Order/PaymentService
system instead, which returned `"Order not found"` (the legacy `Order` table has no
`FO-...` row). **The MPGS checkout controller has never been reachable via real HTTP
traffic since it was wired up** -- no mocked Playwright test or unit test ever caught
this, because none of them exercised the real Express router stack in the real mount
order.

**Repair applied:** moved both routes under the existing `/fixed-orders/` prefix
(`POST /fixed-orders/:orderNo/checkout`, `GET /fixed-orders/:orderNo/payment-status`),
matching the convention already used by the read route directly above them
(`GET /fixed-orders/:orderNo`). Updated `customerApi.ts` and the one mocked Playwright
spec (`p4e-checkout-ui.spec.ts`) that asserted on the old path. Legacy
`order.routes.ts`/`OrderController` untouched. Added a structural regression test
(`r9.2-mpgs-checkout-route-collision-guard.test.ts`) that parses both route files' real
`router.<verb>(...)` registrations and fails if any future change reintroduces a
collision, plus a check that `index.ts`'s mount order (on which this proof depends)
hasn't silently changed.

## 3. Confirmed defect: rate limiter shared one global counter across every route

`rate-limit.middleware.ts` declared its `Map` store at module scope, so **every**
`rateLimit(windowMs, maxRequests)` call site across the whole app -- including the
global `app.use(rateLimit(60_000, 120))` in `index.ts` -- shared one counter keyed only
by IP, regardless of route or configured limit. Any request from an IP to *any*
rate-limited route incremented the same counter consumed by *every other* route's
limiter for that IP, so a route configured for e.g. 10 requests/60s
(`POST /restoration-drafts`) could be exhausted well before that IP had made 10 requests
to that specific route. Found because the dry-run harness's first few real page loads
and API calls were enough to trigger `"Too many requests, please try again later"` on
the very first checkout attempt.

**Repair applied:** each `rateLimit()` call now gets its own private `Map`; a single
shared registry + cleanup interval avoids creating one interval/process listener per
call site. Added `rate-limit.middleware.test.ts` proving two independent limiter
instances for the same IP no longer share a counter.
