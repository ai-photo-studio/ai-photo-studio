# Bank Alfalah MPGS — Sandbox-to-Production Procedure

**Status:** Reference procedure only. No step below has been executed. This
document exists so that once Bank Alfalah resolves the open sandbox blocker
(see `R9.2_MPGS_FINAL_CONTRACT_TABLE_AND_DRIFT_PROTECTION.md` §5), a future
session has an exact, pre-agreed sequence to follow rather than re-deriving one.
**Packet:** R9.2-MERGE-P141-AND-FINAL-BANK-ALFALAH-SUPPORT-PACKET
**Date:** 2026-08-05

## Preconditions (bank-side, not yet met)

1. Sandbox API Password for `merchant.TESTGLOBALINDUS` reissued/reset.
2. REST API access (distinct from MPGS portal login) confirmed enabled for
   the reissued credential.
3. `POST /merchant/{merchantId}/session` confirmed as the correct entry point
   for this profile (or an alternative endpoint supplied instead).

## Step 1 — One sandbox CI run, real result required

Dispatch the existing `bank-alfalah-mpgs-actual-app-e2e.yml` `live` job exactly
once (`mode=live`, exact `confirm_live` string, from `main`) — no new
infrastructure is needed; it already performs the full actual-app flow. See
`R9.2_MPGS_CI_LIVE_PROOF_2026-08-05.md` for what this run does and what it
produced last time (`401`).

## Step 2 — Require `HTTP 2xx` + `session.id`

The run is only a pass if the response is `2xx` **and** a `session.id` (plus
`successIndicator`) is present — `initiateHostedCheckout` already throws if
either is missing (`p4c-bank-alfalah-mpgs-gateway.service.ts`), so this is
enforced by the existing code, not a new check. Do **not** relax that
requirement to "make it pass."

## Step 3 — One sandbox test-card transaction

Only after Step 2 passes: use Mastercard's published MPGS sandbox test card
numbers (from the bank-supplied "Test Cards" documentation link) to complete
exactly one Hosted Checkout redirect through to a test-card charge in the
sandbox UI. This is the first point in the whole integration where card data
is ever entered — it must be a published test card, never a real card, and
never more than once per verification pass.

## Step 4 — Server-side Retrieve Order verification (mandatory, not optional)

After the redirect, the code must never trust the browser's own claim. It must
independently call `retrieveOrder` (`GET .../order/{orderId}`) and verify,
server-side:

- `order.id` matches the stored `PaymentAttempt.gatewayOrderId`,
- `amount` (converted to minor units) matches `PaymentAttempt.amountMinor`,
- `currency` matches `PaymentAttempt.currency`,
- `status` is `PAID`,
- the 3DS result (if present in the retrieved order) indicates a successful
  authentication, not just a submitted attempt.

`matchRetrievedOrderToAttempt` in the existing adapter already implements the
first four checks exactly this way — this step is proving it against a real
gateway response for the first time, not writing new matching logic. The 3DS
result field name/shape is not yet confirmed from documentation and must be
added to `matchRetrievedOrderToAttempt`'s checks (or explicitly confirmed
absent from the response) before this step can be marked complete.

## Step 5 — Prove duplicate return/webhook cannot duplicate payment

This is already proven at the unit/race level (`p4c-bank-alfalah-mpgs-gateway.service.pg-race.test.ts`
— duplicate sequential and concurrent browser-return/webhook-trigger races
converge on exactly one `PaymentEvent`/entitlement/master/execution row, via
`dedupeHash` and the database's own unique constraints). This step is
re-confirming that same guarantee holds against the **real** gateway's actual
webhook payload shape and actual browser-return query-string shape once both
are observed for the first time from Step 3's real transaction — not writing
new idempotency logic.

## Step 6 — Inform Bank Alfalah sandbox/UAT passed

Only after Steps 1–5 all pass. A short, factual status update — not a request
for anything yet.

## Step 7 — Request the production go-live checklist

Only after Step 6. Request, explicitly:
- production Merchant ID and API Password,
- production endpoint/host (if different from the sandbox host),
- PKR and USD enablement confirmation for production,
- webhook security (signature header name/algorithm — still undocumented;
  `handleMpgsWebhookTrigger` currently treats the webhook payload as an
  untrusted trigger only, precisely because this is unconfirmed),
- IP allowlisting requirements for both directions,
- settlement schedule/reporting,
- the bank's own go-live checklist/sign-off requirements.

## Step 8 — One bank-approved low-value production transaction

Only after Step 7's checklist is satisfied and the bank has explicitly
approved a live test. A single, low-value, real transaction, before any public
launch. `BANK_ALFALAH_MPGS_ENABLED` may only be set `true` in a production
environment after this step, and only by an explicit, separate,
owner-authorized action — never as a side effect of any packet in this
directory.

## What stays constant throughout

- Amount, currency, and order ID remain exclusively server-owned at every
  step — never accepted from a client request body. This is already enforced
  and tested; production activation does not change it.
- The webhook handler never trusts webhook content for the payment decision
  by itself — it always re-runs `retrieveOrder` server-side. This does not
  change for production until webhook signature verification is implemented
  and documented (Step 7).
- No step in this procedure is authorization to skip a step, combine two
  steps, or mark a step complete based on a mocked/stubbed response — every
  step above requires a real gateway response.
