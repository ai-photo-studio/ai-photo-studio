**Contradictions recorded, not silently reconciled:**

1. **Merchant ID length.** Generic MPGS documentation states `merchantId` may be
   up to 12 characters; Bank Alfalah confirmed this profile's ID is 15. Resolved
   per standing rule: the bank's merchant-specific confirmation wins, the exact
   15-character ID is always used unmodified, and **no truncated/derived variant
   has ever been tested against the live sandbox**. This contradiction is
   recorded, not resolved — only the bank can resolve it.
2. **`/checkout` vs `/transaction` vs `/session`.** `PUT .../order/{id}/checkout`
   returns `404` with the gateway's own body naming a *different* expected
   segment: `"After url path …/order/{id}, expected /transaction"`

   `/session`, which is what the bank's live V100 doc specifies and the only
   shape that reaches real authentication. Whether this profile is *also*
   provisioned for `/order/{id}/transaction` is unresolved and is a bank
   question, not a client defect.
3. **Content type.** The bank's cURL example implies `text/plain`; the adapter
   sends `application/json`. Both were tested live and behave **identically**
   (§3). Recorded as a non-variable, not reconciled by changing code.

## 3. Why no client-side variable remains

Four independent live probes, across three endpoint shapes and both content
types, all return the same `401`:

| Probe | Request | Result |
|---|---|---|
| A | `POST .../session`, `text/plain` | `401 Invalid credentials.` |
| B | `POST .../session`, `application/json` | `401` — **identical to A** |
| C | `GET .../order/{id}` (Retrieve Order, read-only) | `401` — **identical to A/B** |
| D | `PUT .../order/{id}/checkout` | `404` — gateway names `/transaction` as expected segment |

*(A–D: `P4D_MPGS_FINAL_LOCAL_INVESTIGATION` §3. A/B/C confirm content-type and
endpoint are not the variable; D is the separate structural lead in §1.)*

**The decisive control:** in `P4D_SESSION_ENDPOINT_AUTH_DIAGNOSTIC` §2, the exact
configured password and a **deliberately wrong control password** produced
**byte-identical** `401` responses. The gateway is therefore not distinguishing
this credential at all — it rejects before, or independently of, password
correctness. No change to request construction on this side can alter that
outcome, which is why further client-side probing has no remaining diagnostic
value.

Additionally, the credential bytes were audited without ever printing them
(`P4D_MPGS_FINAL_LOCAL_INVESTIGATION` §2): Merchant ID exactly 15 chars, API
Password exactly 32 chars, no CR/LF/space/tab/quote/BOM/trailing newline in
either; Basic Auth username byte-exact; target URL 101 chars with no encoding
artifact. Transcription error on this side is ruled out.
